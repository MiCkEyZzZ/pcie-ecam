PCIe ECAM Host Bridge

PCIe ECAM Host Bridge

Техническое руководство

Host bridge — корневой мост шины PCI Express: он связывает процессор с деревом устройств PCIe и предоставляет доступ к их configuration space. В современных системах этот доступ почти всегда идёт через ECAM (Enhanced Configuration Access Mechanism) — окно памяти, в которое отображается конфигурационное пространство всех шин, устройств и функций.

Эта книга описывает механизм ECAM, формат configuration space, алгоритм перечисления шины и устройство no_std-драйвера, который всё это реализует.

Окно ECAM — обычная память, но с особыми свойствами:

  • доступ только выровненный, по 4 байта;

  • окно не кэшируется.

Замечание об актуальности

Механизм ECAM стабилен с первых версий PCIe. Меняются расширенные возможности и правила управления питанием, но формула адреса и размер окна на функцию остаются прежними.

1.1. Что такое host bridge

Host bridge — это функция, которая соединяет процессорную сторону системы с шиной PCI Express. Через неё процессор получает доступ к устройствам, а устройства — к памяти.

Что делает мост

ФункцияПояснение
Формирует шину PCIeСоздаёт корневую шину с номером 0
Отображает configuration spaceДелает конфигурацию доступной через окно памяти
Транслирует адресаСопоставляет адреса CPU и адреса шины
Маршрутизирует прерыванияПередаёт INTx и MSI в контроллер прерываний
Ограничивает DMAЧерез IOMMU или окна трансляции

Почему это не «просто мост»

В отличие от моста PCI, корневой комплекс PCIe не является прозрачным. Он:

  • не имеет собственного configuration space;
  • не пересылает конфигурационные транзакции как обычные TLP — в PCIe они идут через механизм ECAM или устаревший механизм через пару портов ввода-вывода;
  • управляет нумерацией шин, а не получает её извне.

Из чего состоит

CPU
 │
 ▼
Host bridge ──▶ корневой порт 0 ──▶ шина 1 ──▶ устройство
 │                         │
 │                         └──▶ шина 2 ──▶ мост ──▶ устройства
 │
 └──▶ окно ECAM (configuration space всех шин)

Корневой комплекс может содержать несколько корневых портов. Каждый порт начинает своё поддерево, но все они обычно видны через одно окно ECAM или через несколько соседних окон.

Что видит программное обеспечение

С точки зрения кода мост — это:

  1. Окно памяти, по которому читается и пишется configuration space.
  2. Набор окон для памяти и ввода-вывода, выделяемых устройствам.
  3. Способ нумерации шин при перечислении.
  4. Маршрутизация прерываний.

Первое — предмет этой книги. Остальное рассматривается лишь настолько, насколько нужно для перечисления и запуска устройств.

Отличие от «моста» в дереве устройств

В дереве устройств термин «мост» означает узел, у которого есть свойство device_type = "pci" и диапазоны ranges. В PCIe терминологии это соответствует корневому комплексу, а не отдельной функции типа 1.

1.2. Место ECAM в топологии PCIe

Configuration space в PCIe доступно двумя способами.

СпособКак работаетПрименение
ECAMОкно памяти, отображённое на все шиныСовременные системы
Механизм #1 / #2Порты 0xCF8/0xCFC или 0xC000Устаревшие x86-системы

ECAM — основной способ. Он описан в базовой спецификации PCIe и обязателен для корневых комплексов; устаревший доступ через порты сохранён только для совместимости со старым программным обеспечением.

Как это выглядит в адресном пространстве

Физическая память

 │ ...                                     │
 ├─────────────────────────────────────────┤
 │ Окно ECAM                               │
 │  bus 0  ─ 32 устройства × 8 функций     │
 │  bus 1                                  │
 │  ...                                    │
 ├─────────────────────────────────────────┤
 │ Окна MMIO устройств                     │
 ├─────────────────────────────────────────┤
 │ ...                                     │

Почему окно, а не транзакции

Configuration-транзакции PCIe адресуются полем Bus/Device/Function в заголовке TLP. Чтобы процессор мог их формировать, нужен специальный контроллер. Вместо этого спецификация предлагает отобразить конфигурацию в память: тогда обращение к памяти превращается в configuration-транзакцию аппаратно.

Это даёт:

  • обычные load/store вместо специальных инструкций;
  • доступ к расширенному пространству до 4 КБ на функцию;
  • единый механизм для всех архитектур.

Что находится за окном

Диапазон смещенияСодержимое
0x000–0x0FFСтандартное пространство PCI
0x100–0xFFFРасширенное пространство PCIe

Стандартные 256 байт совпадают по раскладке с PCI, поэтому драйверы, написанные для PCI, работают и здесь.

Ограничения

  • Окно описывает все шины сегмента, включая несуществующие. Обращение к отсутствующей функции может привести к ошибке шины.
  • Адресация каждой функции фиксирована, поэтому размер окна определяется диапазоном номеров шин.
  • Запись в окно не является атомарной операцией над несколькими регистрами.

Связь с ACPI и деревом устройств

Прошивка сообщает:

  • базовый адрес окна;
  • диапазон шин, который окно покрывает;
  • номер сегмента, к которому относятся эти шины.

В ACPI это таблица MCFG, в дереве устройств — свойства узла pci-host-ecam-generic. Драйвер не должен угадывать адрес.

1.3. Задачи драйвера

Драйвер host bridge решает четыре задачи, и все они связаны с доступом к конфигурации.

1. Найти окно

ИсточникЧто даёт
ACPI MCFGБазовый адрес, сегмент, диапазон шин
Дерево устройствreg, bus-range, linux,pci-domain
Прямая конфигурацияПараметры, заданные при сборке

Драйвер должен уметь работать хотя бы с одним источником, а лучше — с обоими, выбирая доступный.

2. Дать доступ к конфигурации

API должен позволять:

  • читать и писать байт, слово (16 бит) и двойное слово (32 бита);
  • работать с расширенным пространством до 0xFFF;
  • возвращать ошибку при выходе за границы окна;
  • не падать при обращении к отсутствующей функции, если платформа это позволяет обнаружить.

3. Перечислить устройства

Перечисление — обход дерева:

для каждой шины из диапазона:
    для каждого устройства 0..31:
        прочитать vendor ID
        если 0xFFFF — устройства нет
        определить тип заголовка
        если мост — назначить вторичную шину и продолжить рекурсию
        иначе — обойти функции 1..7 при поддержке multi-function

Результат — список функций с их адресами и размерами окон.

4. Подготовить ресурсы

Для каждой функции нужно:

  • определить размеры BAR;
  • выделить адреса в окнах памяти и ввода-вывода;
  • записать адреса обратно в BAR;
  • включить декодирование памяти и ввода-вывода;
  • разрешить bus master для устройств, которым нужен DMA;
  • настроить маршрутизацию прерываний.

ЗадачаКто отвечает
Тренировка линииАппаратура
Управление питанием устройствДрайверы устройств
Загрузка прошивки FPGAДрайвер устройства
Арбитраж доступаЯдро ОС

Минимальный результат

После работы драйвера должно быть возможно:

1. Прочитать vendor/device ID любого устройства.
2. Найти BAR и понять, куда отображена память устройства.
3. Обратиться к регистрам устройства по MMIO.
4. Получить прерывание от устройства.

Если это работает — мост выполняет свою роль.

1.4. Границы применимости

ECAM — не универсальное решение. Есть ситуации, где он не применяется или применяется с оговорками.

Когда ECAM не подходит

СитуацияПричина
Устройство за мостом PCIДоступ зависит от того, преобразует ли мост configuration-запросы
Старая x86-система без MCFGДоступ только через порты 0xCF8/0xCFC
Отсутствие отображения памятиОкно не описано прошивкой
Ограничение на размер окнаДиапазон шин уже, чем всё дерево

Ограничения стандартного пространства

Стандартные 256 байт достаточны, чтобы найти BAR и список возможностей, но не содержат:

  • регистров AER;
  • MSI-X таблицы (только указатель);
  • серийного номера устройства;
  • параметров виртуализации SR-IOV.

Для них нужно расширенное пространство, а значит — полноценные 4 КБ на функцию.

Ограничения платформы

ОграничениеСледствие
Только 32-битные обращенияНельзя использовать байтовые операции
Частичное декодирование адресаНекоторые функции недоступны

Что считать «отсутствующим устройством»

Чтение vendor ID даёт 0xFFFF, если функции нет. Но:

  • некоторые платформы возвращают 0xFFFFFFFF на любое обращение за пределы окна;
  • некоторые возвращают мусор;
  • некоторые генерируют ошибку шины.

Поэтому первое чтение всегда должно быть защищённым: либо аппаратным таймаутом, либо известным диапазоном шин из прошивки.

Совместимость с PCI

Устройства PCI, подключённые через PCIe-мост, видны в ECAM. Их configuration space — те же 256 байт, но расширенное пространство для них не определено.

Итог

Драйвер должен:

  1. брать диапазон шин из прошивки, а не сканировать всё;
  2. проверять выравнивание и разрядность;
  3. уметь работать только с 32-битными обращениями;
  4. не считать, что любое чтение за пределами окна безопасно.

2.1. Обзор механизма ECAM

ECAM отображает configuration space всех функций сегмента в непрерывное окно физической памяти.

Три уровня адресации

segment  →  bus  →  device  →  function  →  offset
УровеньРазрядностьКоличество
segment16 бит65536
bus8 бит256
device5 бит32
function3 бита8
offset12 бит4096 байт

Формула

addr = ECAM_BASE
     + (bus      << 20)
     + (device   << 15)
     + (function << 12)
     + offset

Слагаемые не пересекаются, поэтому адрес вычисляется без таблиц и проверок на пересечение.

Размеры

ЧтоОбъём
Одна функция4 КБ
Одно устройство (8 функций)32 КБ
Одна шина (32 устройства)1 МБ
256 шин256 МБ

Именно 256 МБ — типичный максимальный размер окна для сегмента. На практике прошивка описывает только реально используемый диапазон шин, поэтому окно бывает меньше.

Что находится в окне

ECAM_BASE
 ├── bus 0
 │    ├── dev 0
 │    │    ├── fn 0  (4 КБ)
 │    │    ├── fn 1
 │    │    └── ... fn 7
 │    ├── dev 1
 │    └── ... dev 31
 ├── bus 1
 └── ... bus N

Пустые места тоже присутствуют: окно покрывает все комбинации в диапазоне, независимо от того, есть ли там устройство.

Почему 4 КБ на функцию

ОбластьРазмерНазначение
Стандартная256 байтСовместимость с PCI
Расширенная3840 байтВозможности PCIe

Оставшееся место внутри 4 КБ отведено под расширенные возможности и зарезервировано.

Атрибуты окна

СвойствоЗначение
Тип памятиDevice, не кэшируемая
Выравнивание доступа4 байта

Последний пункт важен: некоторые регистры очищаются при чтении, поэтому «просто посмотреть» не всегда безопасно.

Что делает аппаратура

При обращении к окну контроллер:

  1. Проверяет, что адрес попадает в диапазон.
  2. Выделяет номер шины, устройства и функции.
  3. Формирует configuration-транзакцию.
  4. Возвращает данные или ошибку.

Программное обеспечение видит только обычную память.

Устройства с одной функцией

Устройство может иметь только функцию 0. Признак — бит 7 регистра Header Type (0x0E):

Бит 7Значение
0Одна функция
1Несколько функций

Если бит равен нулю, функции 1–7 проверять не нужно.

Функция 0 как обязательная

Если у устройства несколько функций, функция 0 должна присутствовать. Обратное неверно: отсутствие функции 1 не означает отсутствия функции 2.

Поэтому обход всегда идёт по всем восьми номерам, кроме случая, когда бит multi-function равен нулю.

ARI

При включённом Alternative Routing-ID Interpretation (ARI) нумерация меняется: поле device и младшие биты function объединяются, позволяя до 256 функций на устройстве.

Практическое замечание

Номер шины — не свойство устройства, а результат назначения. При перечислении мост получает вторичную шину, и все устройства за ним видны уже под новым номером. До назначения их адреса не определены.

2.3. Раскладка окна ECAM

Окно ECAM непрерывно, но внутри него действует строгая структура.

Раскладка внутри функции

СмещениеОбласть
0x000–0x03FЗаголовок функции
0x040–0x0FFРегистры, зависящие от типа
0x100–0xFFFРасширенные возможности

Точная граница зависит от типа заголовка: у типа 0 и типа 1 заголовок занимает 64 байта, дальше идут BAR и служебные поля.

Выравнивание

ЧтоТребование
Функция4 КБ
Устройство32 КБ
Шина1 МБ

Из этого следует, что младшие 12 бит адреса функции — это смещение, а старшие биты определяют положение функции в окне.

Пример

ECAM_BASE = 0x4010_0000

Адрес функции 0000:00:03.0:
  0x4010_0000 + (0 << 20) + (3 << 15) + (0 << 12)
= 0x4010_0000 + 0x1_8000
= 0x4011_8000

Адрес регистра Vendor ID (0x00):
  0x4011_8000

Адрес BAR0 (0x10):
  0x4011_8010

Плотность

УровеньСколько адресовСколько занято
Шина1 МБдо 32 × 8 функций
Устройство32 КБдо 8 функций
Функция4 КБдо 4 КБ

Большая часть окна может быть пустой. Это нормально: аппаратура декодирует адрес целиком, а не ищет занятые области.

Окно и диапазон шин

Прошивка описывает не всё 256-мегабайтное пространство, а только используемые шины:

ECAM_BASE ──────────────▶ bus 0
           + 1 МБ ─────▶ bus 1
           + 2 МБ ─────▶ bus 2
           ...
           + N МБ ─────▶ bus N

Размер окна = (end_bus - start_bus + 1) × 1 МБ.

Смещение внутри окна

Если окно начинается не с шины 0, то адрес считается так:

addr = ECAM_BASE + ((bus - start_bus) << 20) + ...

Некоторые реализации всё равно выделяют окно от шины 0, другие начинают с первой используемой. Это нужно проверять по описанию прошивки, а не предполагать.

Чтение за пределами окна

Обращение за границу описанного диапазона:

  • может вернуть 0xFFFFFFFF;
  • может вызвать ошибку шины;
  • может молча зависнуть на медленной шине.

Драйвер обязан проверять границы до вычисления адреса.

Пример разбора

#![allow(unused)]
fn main() {
pub struct McfgEntry {
    pub base: u64,
    pub segment: u16,
    pub start_bus: u8,
    pub end_bus: u8,
}

pub fn parse_mcfg(table: &[u8]) -> impl Iterator<Item = McfgEntry> + '_ {
    let mut off = 0x2C;
    core::iter::from_fn(move || {
        if off + 16 > table.len() { return None; }
        let base = u64::from_le_bytes(table[off..off + 8].try_into().unwrap());
        let segment = u16::from_le_bytes(table[off + 8..off + 10].try_into().unwrap());
        let start_bus = table[off + 10];
        let end_bus = table[off + 11];
        off += 16;
        Some(McfgEntry { base, segment, start_bus, end_bus })
    })
}
}

В системе может быть несколько окон: например, отдельные для встроенных устройств и для слотов. Каждое окно описывается своей записью со своим сегментом.

MCFG

Сегмент — не то же самое, что окно: в одном сегменте может быть несколько окон, покрывающих разные диапазоны шин.

Если MCFG нет

Тогда:

  • платформа не поддерживает ECAM через ACPI;
  • нужен доступ через порты 0xCF8/0xCFC;

Драйвер должен явно сообщать об отсутствии окна, а не пытаться угадать адрес.

Проблема «сегмент 0 по умолчанию»

Многие драйверы предполагают, что существует только сегмент 0. Это неверно для больших систем. Корректная реализация:

  • хранит список окон;
  • ищет окно по номеру сегмента;
  • при отсутствии окна возвращает ошибку, а не использует первое попавшееся.
#![allow(unused)]
fn main() {
pub fn window_for(&self, segment: u16) -> Result<&EcamWindow, Error> {
    self.windows
        .iter()
        .find(|w| w.segment == segment)
        .ok_or(Error::UnknownSegment)
}
}

Несколько окон в одном сегменте

Диапазон шин одного сегмента может быть разбит на несколько окон. Тогда поиск идёт по паре «сегмент + шина»:

#![allow(unused)]
fn main() {
pub fn window_for(&self, segment: u16, bus: u8) -> Result<&EcamWindow, Error> {
    self.windows
        .iter()
        .find(|w| w.segment == segment && w.contains_bus(bus))
        .ok_or(Error::NoWindow)
}
}

Номер сегмента участвует в идентификации источника DMA: IOMMU различает устройства по паре (segment, bus/device/function). Поэтому при включённой трансляции важно сохранять это соответствие.

2.8. Перечисление шины

Перечисление — обход дерева PCIe от корневой шины вниз.

Схема

scan_bus(bus):
    for dev in 0..32:
        vendor = read16(bus, dev, 0, 0x00)
        if vendor == 0xFFFF: continue

        header = read8(bus, dev, 0, 0x0E)
        functions = if header & 0x80 { 0..8 } else { 0..1 }

        for fn in functions:
            vendor = read16(bus, dev, fn, 0x00)
            if vendor == 0xFFFF: continue

            if is_bridge(bus, dev, fn):
                sec = alloc_bus()
                program_bridge(bus, dev, fn, sec)
                scan_bus(sec)
                set_subordinate(bus, dev, fn, max_bus_used)
            else:
                register_function(bus, dev, fn)

Порядок обхода

Обход в глубину:

bus 0
 ├── dev 1 (мост) ──▶ bus 1
 │                     ├── dev 0
 │                     └── dev 2 (мост) ──▶ bus 2
 ├── dev 2
 └── dev 3

Номера шин назначаются по мере спуска: первый мост получает следующий свободный номер, всё его поддерево занимает диапазон, затем нумерация продолжается.

Назначение номеров

ШагДействие
1Взять следующий свободный номер n
2Записать n в Secondary Bus Number моста
3Записать n во временное значение Subordinate Bus Number
4Просканировать шину n
5Записать фактический максимум в Subordinate Bus Number

Шаг 5 важен: во время сканирования мост должен пропускать транзакции ко всем шинам поддерева, иначе обращения к устройствам за ним не дойдут.

Проверка типа

#![allow(unused)]
fn main() {
fn is_bridge(cfg: &impl ConfigSpace, a: Address) -> bool {
    matches!(cfg.read8(a, 0x0E).map(|h| h & 0x7F), Ok(0x01))
}
}

Сканирование ограничено диапазоном из прошивки:

если bus > end_bus:
    остановиться и сообщить об ошибке

    ...
}
}

Выравнивание

Адрес BAR должен быть выровнен на его размер:

addr % size == 0

Для окна 1 МБ подходят адреса 0x...00000, 0x...100000 и так далее.

Порядок распределения

5Включить декодирование в Command

Сортировка по убыванию уменьшает фрагментацию.

Окна моста

Мост тоже имеет окна: Memory Base/Limit, Prefetchable Base/Limit, IO Base/Limit. Они должны покрывать все ресурсы устройств за мостом.

Порядок: сначала записать BAR, затем включить декодирование. Обратный порядок приведёт к обращению по неверному адресу.

Барьеры

После записи BAR и Command нужен барьер, прежде чем обращаться к MMIO устройства:

// гарантировать завершение записи до MMIO

}

Распределение должно быть детерминированным: одинаковый набор устройств при одинаковой конфигурации обязан давать одинаковые адреса. Это важно для воспроизводимости и для отладки.

2.10. Маршрутизация configuration-запросов

ECAM меняет только способ доступа. Сами запросы к конфигурации подчиняются правилам маршрутизации PCIe, и их полезно понимать, иначе ошибки перечисления выглядят необъяснимо.

Два типа запросов

ТипКому адресованЧто содержит
Type 0Устройству на текущей шинеНомер устройства и функции
Type 1Мосту, за которым нужная шинаНомер шины, устройства и функции

Различие принципиальное: Type 0 не проходит через мосты, Type 1 проходит, пока номер шины попадает в диапазон моста.

Что делает корневой комплекс

При обращении к окну ECAM контроллер:

1. Выделяет из адреса bus/device/function/offset.
2. Если bus == номер корневой шины — формирует Type 0.
3. Иначе — формирует Type 1 и отправляет в сторону шины.

Что делает мост

УсловиеДействие
bus вне secondary..=subordinateЗапрос не принадлежит поддереву, мост его не принимает
bus == secondaryПреобразует Type 1 в Type 0 и передаёт на вторичную шину
secondary < bus <= subordinateПередаёт Type 1 дальше без преобразования

Диапазон шин как фильтр

Именно поэтому Subordinate Bus Number должен быть не меньше всех номеров поддерева. Если значение меньше, запрос к дальней шине не попадёт в диапазон, и мост ответит отказом.

мост: secondary = 1, subordinate = 1
запрос к bus 2 → вне диапазона → отказ
запрос к bus 1 → Type 0 на вторичную шину

Обратная ошибка — слишком большой subordinate — приводит к тому, что мост перехватывает запросы к шинам, которые ему не принадлежат.

Что видит программное обеспечение

Правило устройства 0

На шине за мостом обычно присутствует устройство 0: это либо сам мост (для корневого порта), либо первое устройство слота. Некоторые реализации требуют, чтобы device 0 function 0 существовал, прежде чем станут доступны остальные устройства шины.

Практический вывод: перечисление всегда начинается с device 0, а не с первого «интересного» устройства.

Биты статуса 11–14 фиксируют аварийные завершения транзакций:

Бит 10 маскирует INTx. Для функций PCIe, использующих MSI, его обычно устанавливают: старые прерывания не нужны и могут мешать.

fn main() {
pub fn for_each_cap(
    cfg: &impl ConfigSpace,
    a: Address,
    mut f: impl FnMut(u8, u8) -> bool,
) -> Result<(), Error> {
    let status = cfg.read16(a, 0x06)?;
    if status & 0x0010 == 0 {
        return Ok(());          // списка нет
    }

    let mut ptr = cfg.read8(a, 0x34)? & 0xFC;
    let mut guard = 0;

    while ptr != 0 && guard < 48 {
        let id = cfg.read8(a, ptr)?;
        let next = cfg.read8(a, ptr + 1)?;

        if !f(ptr, id) {
            break;
        }
        if next == ptr {
            break;              // защита от петли
        }

        ptr = next & 0xFC;
        guard += 1;
    }
    Ok(())
}
}

2. Пройти список, собрать смещения нужных возможностей.
3. Работать с найденными блоками по их собственным правилам.
4. Не предполагать порядок возможностей в списке.

Почему subordinate важен

Мост пропускает транзакции, если номер шины в адресе попадает в диапазон secondary..=subordinate. Если поставить слишком маленькое значение, устройства за мостом станут недоступны. Если слишком большое — мост будет отвечать на чужие адреса.

Окна и потомки

Memory Base  = min(адресов всех устройств поддерева) & ~0xFFFFF
Memory Limit = max(адресов + размер) | 0xFFFFF

Для prefetchable окон действует то же правило. Важно, чтобы окно моста полностью покрывало окна потомков, иначе часть устройств не будет видна.

Сброс вторичной шины

Бит 6 Bridge Control инициирует сброс шины за мостом. После сброса:

  • устройства теряют настройки BAR;
  • номера шин сохраняются;
  • требуется повторное перечисление поддерева.

Замечание

Мост PCIe типа 1 может не иметь ни одного BAR: его задача — маршрутизация, а не предоставление регистров. Наличие BAR проверяется так же, как у обычной функции.

#![allow(unused)]
fn main() {
pub fn for_each_ext_cap(
    cfg: &impl ConfigSpace,
    a: Address,
    mut f: impl FnMut(u16, u16) -> bool,
) -> Result<(), Error> {
    let mut off = 0x100u16;
    let mut guard = 0;

    while off >= 0x100 && off < 0x1000 && guard < 64 {
        let hdr = cfg.read32(a, off)?;
        let id = (hdr & 0xFFFF) as u16;
        let next = ((hdr >> 20) & 0xFFF) as u16;

        if id == 0 || id == 0xFFFF {
            break;
        }
        if !f(off, id) {
            break;
        }

        off = next << 2;
        guard += 1;
    }
    Ok(())
}
}

Окно ECAM не кэшируется. Но даже при правильных атрибутах страниц возможны переупорядочивания, поэтому после изменения конфигурации нужен барьер:

4.2. Абстракция доступа к конфигурации

Единый интерфейс позволяет перечислению не знать, каким способом получен доступ — через ECAM, через порты или через эмуляцию.

Трейт

#![allow(unused)]
fn main() {
pub trait ConfigSpace {
    fn read8(&self, a: Address, off: u16) -> Result<u8, Error>;
    fn read16(&self, a: Address, off: u16) -> Result<u16, Error>;
    fn read32(&self, a: Address, off: u16) -> Result<u32, Error>;

    fn write8(&self, a: Address, off: u16, v: u8) -> Result<(), Error>;
    fn write16(&self, a: Address, off: u16, v: u16) -> Result<(), Error>;
    fn write32(&self, a: Address, off: u16, v: u32) -> Result<(), Error>;
}
}

Почему &self, а не &mut self

Доступ к конфигурации — это операция над внешним устройством, а не изменение локального состояния. Внутренние поля (список окон) не меняются, поэтому достаточно разделяемой ссылки. Изменяемость обеспечивается volatile-записями.

Реализация для ECAM

#![allow(unused)]
fn main() {
pub struct Ecam {
    windows: [EcamWindow; MAX_WINDOWS],
    count: usize,
    lock: SpinLock,
}

impl ConfigSpace for Ecam {
    fn read32(&self, a: Address, off: u16) -> Result<u32, Error> {
        let addr = self.resolve(a, off, 4)?;
        // SAFETY: адрес проверен по границам окна
        Ok(unsafe { core::ptr::read_volatile(addr as *const u32) })
    }

    fn write32(&self, a: Address, off: u16, v: u32) -> Result<(), Error> {
        let addr = self.resolve(a, off, 4)?;
        // SAFETY: см. выше
        unsafe { core::ptr::write_volatile(addr as *mut u32, v) };
        Ok(())
    }
}
}

4.3. Вычисление адреса

Преобразование (segment, bus, device, function, offset) в адрес памяти — центральная операция драйвера.

Формула

#![allow(unused)]
fn main() {
pub fn offset_in_window(bus: u8, device: u8, function: u8, off: u16) -> usize {
    ((bus as usize) << 20)
        | ((device as usize & 0x1F) << 15)
        | ((function as usize & 0x07) << 12)
        | (off as usize & 0xFFF)
}
}

С учётом начала окна

#![allow(unused)]
fn main() {
pub fn resolve(window: &EcamWindow, a: Address, off: u16, width: usize)
    -> Result<usize, Error>
{
    if a.segment != window.segment {
        return Err(Error::WrongSegment);
    }
    if a.bus < window.start_bus || a.bus > window.end_bus {
        return Err(Error::BusOutOfRange);
    }
    if a.device > 31 || a.function > 7 {
        return Err(Error::BadAddress);
    }
    if off as usize + width > 0x1000 {
        return Err(Error::OutOfRange);
    }

    let rel = a.bus.wrapping_sub(window.start_bus) as usize;
    let base = window.base
        + (rel << 20)
        + ((a.device as usize) << 15)
        + ((a.function as usize) << 12)
        + (off as usize);

    Ok(base)
}
}

Порядок проверок

ШагПроверкаПочему
1СегментОкно принадлежит одному сегменту
2Шина в диапазонеНе выходить за описанное окно
3Устройство и функцияУложиться в 5 и 3 бита
4Смещение и ширинаНе выйти за 4 КБ
5ВыравниваниеТребование платформы

Дешёвые проверки идут первыми, чтобы не вычислять адрес зря.

Переполнение

При usize = 32 бита адрес окна плюс 256 МБ может переполниться. Проверка:

#![allow(unused)]
fn main() {
let addr = window.base.checked_add(delta).ok_or(Error::Overflow)?;
}

На 64-битных платформах переполнение маловероятно, но проверка не мешает.

Несколько окон

#![allow(unused)]
fn main() {
fn resolve(&self, a: Address, off: u16, width: usize) -> Result<usize, Error> {
    for w in &self.windows[..self.count] {
        if w.segment == a.segment
            && a.bus >= w.start_bus
            && a.bus <= w.end_bus
        {
            return resolve(w, a, off, width);
        }
    }
    Err(Error::NoWindow)
}
}

Линейный поиск по небольшому массиву быстрее, чем хеш-таблица, и не требует alloc.

Проверка выравнивания

#![allow(unused)]
fn main() {
if (off as usize) % width != 0 {
    return Err(Error::Misaligned);
}
}

Для width = 1 проверка всегда проходит. Для 2 и 4 — отсекает некорректные обращения до записи в память.

Кэш вычислений

Если перечисление обращается к одной функции много раз, полезно хранить вычисленную базу функции:

#![allow(unused)]
fn main() {
fn function_base(&self, a: Address) -> Result<usize, Error> {
    self.resolve(a, 0, 1)
}
}

4.4. Чтение и запись

Реализация доступа должна быть одновременно быстрой, безопасной и переносимой.

Базовые операции

#![allow(unused)]
fn main() {
impl Ecam {
    fn read32_raw(&self, addr: usize) -> u32 {
        // SAFETY: addr получен из resolve и указывает в окно ECAM
        unsafe { core::ptr::read_volatile(addr as *const u32) }
    }

    fn write32_raw(&self, addr: usize, v: u32) {
        // SAFETY: см. выше
        unsafe { core::ptr::write_volatile(addr as *mut u32, v) }
    }
}
}

Почему volatile

Компилятор не знает, что за адресом находится устройство. Без volatile он может:

  • удалить «лишнее» чтение;
  • объединить две записи;
  • переставить обращения местами.

volatile запрещает такие преобразования, но не обеспечивает барьер между разными обращениями.

Запись 16 и 8 бит через слово

#![allow(unused)]
fn main() {
fn write8_via_word(&self, a: Address, off: u16, v: u8) -> Result<(), Error> {
    let aligned = off & !3;
    let shift = (off & 3) * 8;

    let old = self.read32(a, aligned)?;
    let mask = !(0xFFu32 << shift);
    let new = (old & mask) | ((v as u32) << shift);

    self.write32(a, aligned, new)
}
}

Опасность: чтение слова затрагивает соседние байты, которые могут быть регистрами со побочными эффектами. Поэтому такой путь применяется только там, где это безопасно, — например, для BAR и Command.

#![allow(unused)]
fn main() {
fn validate(w: &EcamWindow) -> Result<(), Error> {
    if w.base % 0x1000 != 0 {
        return Err(Error::Misaligned);
    }
    if w.start_bus > w.end_bus {
        return Err(Error::BadAddress);
    }
    let size = ((w.end_bus as usize) - (w.start_bus as usize) + 1) << 20;
    let end = w.base.checked_add(size).ok_or(Error::Overflow)?;

    if overlaps_ram(w.base, end) {
        return Err(Error::Forbidden);
    }
    Ok(())
}
}

Почему проверка перекрытия с RAM обязательна

Если окно ECAM по ошибке указывает на обычную память, то:

  • чтение вернёт содержимое памяти, а не конфигурацию;
  • запись испортит данные;
  • ошибки будут выглядеть как «устройство с странным ID».

Проверка на пересечение с картой памяти выполняется один раз при инициализации.

4.7. Состояние перечисления

Перечисление — рекурсивный обход, но рекурсия в no_std нежелательна: стек ограничен.

Итеративный вариант

#![allow(unused)]
fn main() {
pub struct Enumerator {
    stack: [Frame; 16],
    depth: usize,
    segment: u16,
    next_bus: u8,
    max_bus: u8,
}

pub struct Frame {
    pub bus: u8,
    pub device: u8,
    pub function: u8,
    pub last_function: u8,
    pub phase: Phase,
}

pub enum Phase {
    /// Проверка функции 0 и чтение типа заголовка.
    Probe,
    /// Перебор функций устройства.
    Functions,
    /// Запись subordinate после обхода поддерева.
    AfterBridge { bridge: Address },
}
}

Смысл фаз

ФазаЧто делает
ProbeЧитает Vendor ID и Header Type, решает, сколько функций проверять
FunctionsПеребирает функции, для мостов спускается ниже
AfterBridgeЗаписывает фактический subordinate и возвращается к перебору

Шаг обхода

#![allow(unused)]
fn main() {
pub fn step(&mut self, cfg: &impl ConfigSpace)
    -> Result<Option<Address>, Error>
{
    loop {
        let Some(frame) = self.stack.get_mut(self.depth) else {
            return Ok(None);                    // обход закончен
        };

        match frame.phase {
            Phase::Probe => {
                let a = Address {
                    segment: self.segment,
                    bus: frame.bus,
                    device: frame.device,
                    function: 0,
                };

                if cfg.read16(a, 0x00)? == 0xFFFF {
                    self.pop();
                    continue;
                }

                let hdr = cfg.read8(a, 0x0E)?;
                frame.last_function = if hdr & 0x80 != 0 { 7 } else { 0 };
                frame.function = 0;
                frame.phase = Phase::Functions;
            }

            Phase::Functions => {
                let fn_no = frame.function;
                let a = Address {
                    segment: self.segment,
                    bus: frame.bus,
                    device: frame.device,
                    function: fn_no,
                };

                if cfg.read16(a, 0x00)? != 0xFFFF {
                    if cfg.read8(a, 0x0E)? & 0x7F == 0x01 {
                        let sec = self.alloc_bus()?;
                        cfg.write8(a, 0x18, frame.bus)?;
                        cfg.write8(a, 0x19, sec)?;
                        cfg.write8(a, 0x1A, sec)?;

                        frame.phase = Phase::AfterBridge { bridge: a };
                        self.push(sec, 0)?;
                        continue;
                    }
                    return Ok(Some(a));         // обычная функция
                }

                if fn_no >= frame.last_function {
                    self.pop();
                } else {
                    frame.function += 1;
                }
            }

            Phase::AfterBridge { bridge } => {
                let max = self.max_bus;
                let b = *bridge;
                cfg.write8(b, 0x1A, max)?;
                frame.phase = Phase::Functions;
                frame.function += 1;
            }
        }
    }
}
}

max_bus хранит наибольший выданный номер. При возврате из поддерева он записывается в Subordinate Bus Number моста. Если бы там осталось значение, выданное при спуске, мост не пропускал бы транзакции к шинам, назначенным позже.

Номера шин не заданы заранее: их назначает драйвер при обходе.

Выделение

#![allow(unused)]
fn main() {
pub struct BusAllocator {
    next: u8,
    end: u8,
}

impl BusAllocator {
    pub fn alloc(&mut self) -> Result<u8, Error> {
        if self.next > self.end {
            return Err(Error::NoResources);
        }
        let b = self.next;
        self.next += 1;
        Ok(b)
    }

    pub fn highest_used(&self) -> u8 {
        self.next.saturating_sub(1)
    }
}
}

Исходно: next = 1, end = 8.

Запись subordinate

Пока идёт обход поддерева, мост должен пропускать все шины под ним. Поэтому:

1. secondary = новый номер
2. subordinate = 0xFF (временно) или новый номер
3. обход
4. subordinate = фактический максимум

Вариант с 0xFF проще, но делает мост слишком «широким»: он будет отвечать на транзакции к шинам, которых нет.

Проверка диапазона

#![allow(unused)]

    return Err(Error::BusOutOfRange);
}
}

Диапазон берётся из MCFG или bus-range. Сканирование за его пределами может привести к зависанию.

Сброс шины

Бит 6 в Bridge Control сбрасывает вторичную шину:

После сброса поддерево нужно перечислить заново: BAR устройств обнулятся.

4.9. Размещение BAR

Размещение ресурсов — самая заметная часть работы драйвера, потому что ошибки здесь проявляются как «устройство не отвечает».

Алгоритм

1. Собрать запросы: (адрес функции, номер BAR, размер, тип).
2. Определить окна платформы для памяти и ввода-вывода.
3. Разместить запросы от большего к меньшему.
4. Записать адреса в BAR.
5. Обновить окна мостов.
6. Включить декодирование.

Запрос

#![allow(unused)]
fn main() {
pub struct BarRequest {
    pub addr: Address,
    pub bar: u8,
    pub size: u64,
    pub is_io: bool,
    pub prefetchable: bool,
    pub is_64: bool,
}
}

Сбор

#![allow(unused)]
fn main() {
fn probe_bars(cfg: &impl ConfigSpace, a: Address) -> Result<(), Error> {
    let mut bar = 0u8;

    while bar < 6 {
        let off = 0x10 + 4 * bar as u16;
        let orig = cfg.read32(a, off)?;

        if orig == 0 {
            bar += 1;
            continue;
        }
        if orig & 1 == 1 {
            // окно ввода-вывода
            let size = measure_io_bar(cfg, a, bar)?;
            record_bar(a, bar, size, true, false, false)?;
            bar += 1;
        } else {
            let is_64 = (orig >> 1) & 3 == 2;
            let prefetchable = (orig >> 3) & 1 == 1;
            let size = if is_64 {
                measure_bar64(cfg, a, bar)?
            } else {
                measure_bar32(cfg, a, bar)?
            };

            record_bar(a, bar, size, false, prefetchable, is_64)?;
            bar += if is_64 { 2 } else { 1 };
        }
    }
    Ok(())
}
}

Измерение

#![allow(unused)]
fn main() {
fn measure_bar32(cfg: &impl ConfigSpace, a: Address, bar: u8) -> Result<u64, Error> {
    let off = 0x10 + 4 * bar as u16;
    let orig = cfg.read32(a, off)?;

    cfg.write32(a, off, 0xFFFF_FFFF)?;
    let mask = cfg.read32(a, off)?;
    cfg.write32(a, off, orig)?;

    let size = (!(mask & !0xF)).wrapping_add(1) as u64;
    Ok(size)
}
}

Для 64-битного BAR измерение охватывает два слова:

mask64 = (read32(off + 4) as u64) << 32 | read32(off)
size   = (!mask64) + 1

Выделение адреса

#![allow(unused)]
fn main() {
pub struct Region {
    pub start: u64,
    pub end: u64,
    pub next: u64,
}

impl Region {
    pub fn alloc(&mut self, size: u64, align: u64) -> Option<u64> {
        let aligned = (self.next + align - 1) & !(align - 1);
        if aligned + size > self.end {
            return None;
        }
        self.next = aligned + size;
        Some(aligned)
    }
}
}

5.1. ACPI и MCFG

На платформах с ACPI окно ECAM описывается таблицей MCFG.

Путь получения

RSDP → XSDT → таблица с сигнатурой MCFG → записи окон
ШагЧто делаем
1Найти RSDP (в памяти или через UEFI)
2Проверить контрольную сумму
3Взять XSDT (или RSDT для 32-бит)
4Пройти таблицы, найти MCFG
5Проверить длину и контрольную сумму
6Разобрать записи

Разбор

#![allow(unused)]
fn main() {
pub fn read_mcfg(table: &[u8]) -> Result<HeaplessVec<McfgEntry, 8>, Error> {
    if table.len() < 0x2C || &table[0..4] != b"MCFG" {
        return Err(Error::BadAddress);
    }

    let len = u32::from_le_bytes(table[4..8].try_into().unwrap()) as usize;
    if len > table.len() || len < 0x2C {
        return Err(Error::BadAddress);
    }

    let mut out = HeaplessVec::new();

    for chunk in table[0x2C..len].chunks_exact(16) {
        let base = u64::from_le_bytes(chunk[0..8].try_into().unwrap());
        let segment = u16::from_le_bytes(chunk[8..10].try_into().unwrap());
        let start = chunk[10];
        let end = chunk[11];

        if start > end {
            continue;
        }
        out.push(McfgEntry { base, segment, start, end })?;
    }
    Ok(out)
}
}

5.3. Особенности реализаций

Спецификация описывает поведение, но кремний бывает строже или снисходительнее. Ниже — типичные отклонения.

Доступ только по 32 бита

Многие контроллеры не поддерживают байтовые и полусловные обращения к ECAM.

РеализацияПоддержка
Полная8, 16, 32
Типичная32
Строгая32, выровненные

Решение: реализовать read8/read16 через 32-битное слово с маской. Ограничение: побочные эффекты соседних регистров.

Отсутствие таймаута

Если контроллер не сообщает об ошибке при обращении к пустой функции, шина может подвиснуть.

МераЭффект
Ограничить диапазон шинНе выходить в пустоту
Сканировать только известные слотыМеньше риска
Использовать bus-range из прошивкиТо же

Возврат мусора

Некоторые платформы возвращают не 0xFFFF, а произвольные значения для отсутствующих функций.

#![allow(unused)]
fn main() {
fn looks_absent(vendor: u16, device: u16) -> bool {
    vendor == 0xFFFF || vendor == 0x0000 || vendor == 0x0001
        || device == 0xFFFF || device == 0x0000
}
}

Проверка эвристическая: реальные устройства с vendor 0x0001 не встречаются, но правило всё равно стоит держать в одном месте.

Окно начинается не с шины 0

ECAM_BASE соответствует bus 0x40, а не 0x00

Тогда смещение считается от start_bus. Ошибка в этом месте даёт «устройства есть, но не те».

Несколько функций на устройстве

Признак multi-function может быть выставлен некорректно. Надёжнее проверять vendor ID каждой функции, а не доверять биту 7:

#![allow(unused)]
fn main() {
for fn in 0..8 {
    if cfg.read16(a.with_function(fn), 0x00)? != 0xFFFF {
        probe(a.with_function(fn))?;
    }
}
}

Доступ к конфигурации — только часть работы моста. Устройствам нужно ещё писать в память.

1. Перед передачей буфера устройству — сбросить кэш на память.
2. После получения данных — инвалидировать кэш.

В дереве устройств когерентность выражается свойством dma-coherent у узла моста.

Пример

#![allow(unused)]
fn main() {
pub fn prepare_dma(
    cfg: &impl ConfigSpace,
    a: Address,
    buf_phys: u64,
) -> Result<(), Error> {
    if buf_phys > u32::MAX as u64 && !supports_64bit_dma(cfg, a)? {
        return Err(Error::Unsupported);
    }

    let mut cmd = cfg.read16(a, 0x04)?;
    cmd |= 0x0002 | 0x0004;
    cfg.write16(a, 0x04, cmd)?;
    fence();

    Ok(())
}
}

Вычисление адреса

static void __iomem *pci_ecam_map_bus(struct pci_bus *bus,
                                      unsigned int devfn,
                                      int where)
{
    struct pci_config_window *cfg = bus->sysdata;
    unsigned int busn = bus->number;
    void __iomem *base;

    if (!cfg || busn < cfg->busn_start || busn > cfg->busn_end)
        return NULL;

    base = cfg->win + ((busn - cfg->busn_start) << cfg->ops->bus_shift);
    base += (PCI_SLOT(devfn) << 15) + (PCI_FUNC(devfn) << 12);

    return base + (where & ~3);
}

Общая функция доступа

static int pci_ecam_read(struct pci_bus *bus, unsigned int devfn,
                         int where, int size, u32 *val)
{
    void __iomem *addr = pci_ecam_map_bus(bus, devfn, where);

    switch (size) {
    case 1: *val = readb(addr + (where & 3)); break;
    case 2: *val = readw(addr + (where & 2)); break;
    case 4: *val = readl(addr); break;
    default: return PCIBIOS_BAD_REGISTER_NUMBER;
    }
    return PCIBIOS_SUCCESSFUL;
}

Функции readb/readw/readl уже содержат нужные барьеры и работу с volatile.
